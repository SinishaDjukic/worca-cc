- The terminal `_execStep` persist fires inside `_execute`'s `finally`, which runs BEFORE the scheduler's `settle()`/`snap()`. So that write carries the PREVIOUS snapshot. In a strictly sequential graph the next execution's `start` write hides the lag almost completely. The bug only shows with parallel executions, or with a wait on a gate or question. A test that just reads the DB inside the next runner cannot see it.
- Recipe to catch it deterministically: override `orch._execute` on the instance. `_engineRun` binds `this._execute` at run time, so the override is honored. On the 2nd `args.node.kind === 'agent'` call, `await setImmediate` and then read `pipelines.resume_point`, before calling the original. At that point execution #1 has settled but nothing else has written the row.
- `writeState` is `async`, but its `tx()` runs synchronously at call time. Persists are therefore already ordered, and the only real cost is write volume. Coalesce writes; there is nothing to serialize.
- `scheduler.reattach()` never calls `snap()`. `_resume()` therefore keeps the saved point (`state.resumePoint = rp`) until the first completion's `onSnapshot` replaces it; never null it there, or a crash before that completion leaves an unresumable row.
- On dev 4034278b (checked 2026-10-21) there is NO `src/core/process-tree.mjs`, whatever older notes say. `claude` children are spawned detached ONLY under agent isolation (`engines/spawn.mjs` `superviseSpawn`: `agentId ? { detached: true }`), and no `process.on('exit')` hook reaps them. Only script and action children have one (`graph/script-runner.mjs`, `actions/spawn.mjs`). A `process.exit()` therefore leaves a live `claude` child behind. Only the runner's abort, SIGTERM and then SIGKILL after `WORCA_SIGKILL_GRACE_MS` (5 s), ends it. Abort reaches the single pid with `child.kill`, not the agent's Bash-tool grandchildren.
- `script-runner.mjs` imports `claude-runner.mjs`. A registry shared by both must live in a third module to avoid an import cycle.
- The execution-#2 recipe relies on `wf_default` having no flow card between `n_clarify` and `n_plan`. A non-agent execution between two agents writes the row at its own start, carrying the new point, and masks the bug.
- To resume in a test after forging a crash, park the first run with a pause; never let it finish `done`. The `finally` of a done run runs `_teardownRunRoot`, which deletes the worktree the resume needs.
- The `worca` CLI handles SIGINT and, since #441, SIGTERM (`attachAndDrive`; SIGTERM pauses with reason `terminated` via `pauseForSignal`). SIGHUP still kills it by the default action, which skips `process.on('exit')`. A detached child therefore survives unless a signal fallback kills the tracked trees.
- A pause during a resume's setup has two traps. `resume()` stays `idle` while it claims the row and reattaches checkouts (seconds), and `pause()` refuses any status but `running`. Then the graph engine's `_restoreFromResumePoint` (orchestrator.mjs) clears the pause reason a SECOND time, after `_resume` already did. A reasoned pause taken in that window (SIGTERM, drain) came back `paused` with reason null, so it did not report to the source. The clear now runs only `if (!this.pauseRequested)`. The test passed alone and failed in the full file (it depends on timing): drive it in-process with `const p = orch.resume(); orch.pauseForSignal('SIGTERM'); await p` (test/writeback.test.mjs).
- CLI-spawn resume tests must seed with `seedPipeline(realpath'd projDir, {status, resumePoint: graphResumePoint(...)})` and run with `{ cwd: projDir }`. `seedPipelineRow` has no resumePoint and its default projectKey matches no cwd, so the CLI exits at "no resume point" or "not onboarded" before it reaches `createOrchestratorFor`.
- `tx()` in `db.mjs` is not re-entrant: calling it inside another `tx` throws. `artifacts.mjs` does not import `prepare`; use `getDb().prepare`.
- `wireRun` in `ui/server.mjs` forces `entry.status = 'error'` on any `error` event. Surface non-fatal problems on a finished run with a different event name.
- `_resume()` claims the DB ROW (an atomic `paused|interrupted -> running` compare-and-set) BEFORE `_engineRehydrate`. A test that passes a forged `resume: { row: { status: 'paused' } }` needs a matching DB row: `createPipeline` leaves it `created`, so `UPDATE pipelines SET status='paused'` first; a row missing from the DB fails with "not found" before any engine check.
- `test/server-pause-resume.test.mjs` shares one `runs` Map across tests, and `/api/resume` there starts a REAL resumed run that is still live later in the file. A test that iterates `runs` (e.g. shutdown pausing) must park the other entries aside, or it counts them.
- `test/host-guard-wiring.test.mjs` fails ("no WORCA_HOST_PID") when the suite is launched from inside a worca-driven agent, which inherits `WORCA_HOST_PID`. Run the suite with `env -u WORCA_HOST_PID npm test` there; it is not a regression.
- `resume()` calls `_setStatus('running')`, which emits the first `state` event, BEFORE its first `await this._persist()`. A test that reads the `pipelines` row inside the first `state` handler sees the row the pause left, not the resumed state. To assert what the resumed run persists, wrap `orch._persist` on the instance and read the row after the first real call returns.
- Totals derived from `state.steps` (`totalActiveMs`, `totalCostUsd`) must be recomputed in `resume()` after the steps are rehydrated. Otherwise they start at the constructor's 0 and are written to the row as 0.
- A plain error thrown during resume setup (e.g. an instance override of `orch._registerEngineConfig`) does NOT end an `auto: true` mock run as `error`: the failure policy parks it and `resume()` resolves `paused` (seen 2026-10-17). To drive the `error` finally (teardown, `_finishExecEnv`), throw `markTerminal(err)` (failure-policy.mjs). A run that re-pauses before it reconnected must keep the saved `resumePoint.execEnv` (orchestrator falls back to `_savedExecEnv`), or its parked E2B sandbox is orphaned.
- That pause (any failure before `_engineRun`, e.g. in `_resumeExecEnv`) is built from the CONSUMED point `rp`:
  `state.resumePoint` was nulled when the row was claimed, and `_engineLastPoint()` is null because `_graphSnapshot` is
  restored only in `_restoreFromResumePoint`, inside `_engineRun`. So reassigning `this._savedExecEnv` there does not
  reach the paused point (seen 2026-10-22, E2B resume fix): `rp.execEnv` keeps the old record. A sandbox released
  there stays named in the point; the next resume connects, finds it gone, and starts a fresh one.
