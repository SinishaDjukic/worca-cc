Dev's Chats column (#948 s2/s3, #953 retired the `chatsColumn` flag and the old History column) broke a side-chat branch in five silent ways while merging cleanly in app.js/style.css (PR 954 merge, 2026-10-25). See also [[ask-ui-hidden-pins]].

- `mountChatsColumn({host})` does `host.replaceChildren(head, chip, list, bar)`: anything added to `aside.chat-history` in `buildHistory` vanishes. Append extras AFTER the mount (in `mountChats`).
- The column owns the thread list (no `renderHistory`, no `?q=` search — search lives in the top bar's Chats group). A consumer of the rows reads them through `mountChatsColumn`'s `onThreads(threads, view)` (called on every paint); only `view.show === 'all'` is the whole list, and pinned chats lead it (sort yourself for "newest"). TRAP (cycle-1 major): the view is restored from localStorage (`worca-cc.chats.view`), so a consumer that listens only while `show === 'all'` NEVER fires for someone who left the list on Needs you/Archived (the dock's Recent chats + History button vanished; jsdom proof: `bootChat({ local: { 'worca-cc.chats.view': '{"show":"needs"}' } })`). Settled (cycle 2): `onThreads(threads, view, { loaded, newest })`. `newest` is true for the All view in activity order or with no more pages; there the list itself gives the rows. Otherwise the panel calls its own `loadRecent()`, which asks `?show=all&sort=activity&limit=CHATS_PAGE`. Do NOT ask with `limit=3`: `listThreadsPage` orders pinned chats first, so 3 rows are the pinned ones. Skip the callback while `!loaded`, because `setView` paints `[]` first. Also skip it while the array is the same one, because a selection repaint passes it again.
- Removing a recent row has two sources. `dropRecent` (delete, history clear, Delete group) is one; the refetch after the action is the other, and it drops the row too, so a mutant of `dropRecent` stays green. To pin `dropRecent`, make every `/api/ask/threads?` read fail after the action (`state.down` in `test/ask-panel-side.test.mjs`).
- `loadRecent` open edges (cycle-2 review minors, not fixed in that run). (1) It clears `recentStale` before the fetch and never sets it again on failure. `onShow` → `setHost('dock')` is a no-op while the host is already dock, and `openPage` retries only `historyStale`, so one failed `show=all` read under Needs you hides Recent + History until the next refresh frame. (2) `dropRecent` never bumps `recentGen`, so a fetch already in flight puts a just-deleted chat back. A fix needs a test that fails a `loadRecent` read WHILE rows show: the `failed read keeps rows` and `st.destroyed` mutants stay green on every existing test.
- `test/ui-chat-style.test.mjs` bans the OLD class names anywhere in style.css (`ask-thread-(row|pick|dot|col|title|meter|when|fill|topics|match)`, `chat-history-(head|…|body|…)`, `chat-new-btn`): reused markup needs new names.
- `.chat-page[data-chats="on"] .chat-history` (and its 1099px media twin) is (0,3,0) and `data-chats="on"` is always set: any `.chat-page[data-x] .chat-history` override ties and must come AFTER dev's block. Dev also hides the composer meter (`[data-chats="on"] [data-ask-meter]`) for the head's `.chat-head-meter`, and adds `.chat-new-plus` + `.runs-resize` (absolute, in the aside) — a re-host must hide or restate each.
- `onChatKeys` is a DOCUMENT listener gated only on `st.open` (⌘\, ⇧⌘L, ⌥⌘N, ⌥↑/↓, `?`); the column's menus, group picker and keys sheet append to `body` (outside `el.page`). A host showing the panel beside another page must gate keys to `el.page.contains(target)` and exempt `.wfv-menu, .group-picker, .keys-modal` from outside-press closes.
- `onChatKeys` is BUBBLE and registered at `createAskPanel` (late in app.js), so every app.js document keydown listener registered earlier runs first and its `preventDefault` silences the panel (`e.defaultPrevented`). Dev's Runs `?` listener (app.js, after the Runs Escape arm; active on every route the Runs section renders) opens the RUNS keys sheet when `?` is pressed on a non-field control inside `#ask-side`: the Chat sheet is unreachable from the column there, while on `#schedules` it works. Fixed in cycle 2, pinned in `ui-ask-side-shell`. Every NEW page-level document key listener needs the same `if (e.target?.closest?.('#ask-side')) return;` the Escape arms got. jsdom proof: `bootChat`, `go('runs')`, click `#topnav-ask`, focus `#ask-side [data-ask-side-thread]`, dispatch a bubbling cancelable `KeyboardEvent('keydown', {key:'?', shiftKey:true})`, read `.keys-modal .keys-h` (Runs: "Runs list"; Chat: "Chat page").
- Same root cause for Escape: the `#ask-side` exemptions in app.js's capture-phase Escape arms miss the column's body-level `.wfv-menu`/`.group-picker`. History/Running arms stand down (`runsListOwnsEscape()` checks those selectors), the Runs selection arm too; the PROJECT page arm (`leaveProjDetail`) and the `#workspace-create` arm (`wizClose.click()`) did not. Since cycle 2 they carry their own `if (document.querySelector('.wfv-menu, .group-picker, .label-picker')) return;` line. A new capture-phase page arm needs that line too (`.keys-modal` is a `.viewer-modal`, so `dialogOpen` already covers it). Escape in a chat row's ⋯ menu opened from the side column on `#projects/<key>` closes the menu AND goes to `#projects` (bootChat probe: `go('projects/<key>')`, open the column, click the title, click `.runs-more`, dispatch Escape on the menu item, read `location.hash`).
- Dev paths that remove chats bypass `deleteThread`: `onChatsGone` (Delete group) and `chatsCol.onFrame` (history clear). Per-chat state kept elsewhere (unread dot, recent rows) needs its own cleanup there.
- Old-column tests: the trash is now ⋯ › Delete… (`deleteFromList(ctx, id)` in `test/helpers/ask-panel-harness.mjs`); views via `#chats-view-btn` → `.wfv-menu [role="menuitemradio"]`.

## Dev #958 (keep the view across replies) vs the side column (PR 954 merge 2, 2026-10-27)
- A bare `t.scrollTop = x; t.dispatchEvent(new Event('scroll'))` no longer unpins: with no wheel/key/press before it, the scroll counts as a layout clamp. Old-branch tests then fail their "Jump to latest shows" precondition. Use the harness's `userScroll(ctx, t, x)`, which is how dev's own tests were adapted.
- `closePage` saves `st.leftAt = {threadId, top, pinned, host}`, and `openPage` writes `top` back as raw pixels. Settled: restore only from the Chat page back to the Chat page (`back.host === 'page' && st.host === 'page'`). Every other case shows the chat at the bottom, as the side column always did, because:
  - the column slides in from 0px wide (`.is-entering`), and `applyPin` restores on the first frame with `clientHeight > 0`;
  - a host move changes the width, so the same pixel offset lands on another message.
  - Pinned by `test/ask-panel-side.test.mjs` "#958 keeps a reader's place from the Chat page to the Chat page only"; jsdom alone cannot show the wrong landing.
- Seams found in the merge audit and left open:
  - dev's `.chat-dock::before` fade (`--chat-dock-fade`, 32px) covers the bottom of `.ask-side-empty`;
  - `graph/proposal-host.mjs` sizes a proposal's well height once (`sized`), from the first width it sees (mid-slide or the other host);
  - `onScrollKey` treats a key pressed with the focus on `<body>` as the reader scrolling, even in the column, where that key belongs to the page.
- Contract: a transcript focus keeper (#958 `keepFocus(el.transcriptCol)`, ended only by a document pointerdown or a focusout WITH a relatedTarget) must also end in `closePage` (`focusKeep.stop()`). Hidden, its restore is a no-op in Chrome; after a route that fires no document event (browser Back, Alt+←) the column shows the panel VISIBLE with the focus on `<body>`, and the next in-place move of the kept control pulls the focus into the column. jsdom proof (~0.1 s): `applyFlags({commandSummaries:true})`, one command row, focus `.ask-cmd-row-btn`, `close()` → move root → `setHost('dock')` → `open(undefined,{focus:false})`, then push an `ask-message` with a second command: the first row MOVES into `.ask-cmd-gbody`.
- Dev #970 pointer selection (`list-dom.mjs` `bindPointerSelect`, capture on the list) is clean in the column (jsdom, 1400/900px: selects there only, no route, no `uncover`). Probe trap: the long-press toggle repaints and REPLACES the row; a jsdom click on the held, detached `a.runs-row` follows its href to `#chat/<id>` (false "navigates"). Re-query the row first.
