Set up Worca in five answers

A setup assistant that runs on the first start and from Settings › General. It asks about the network, where models come from, which models to use, and how hands-on you want to be. Then it writes every setting, signs in, imports models and tests them for you. A team lead can publish shared defaults once (model roles, limits, conventions); each person still sets up their own network and model sources.

The missing piece: model roles

Worca has no default model today. Each slot either names a model or falls back to a built-in Claude one. The assistant needs one place to write, so the concept adds three roles that every slot inherits from.

A role names the work, not the model

The three roles line up roughly with Opus, Sonnet and Haiku, but they are named after the kind of work so they still make sense on Copilot, OpenAI or Ollama. Each role holds one model and one effort, which you pick. "Deep thinking = GPT-5.5 via Copilot" is valid, and so is "Quick jobs = Sonnet" if you care more about quality than cost.

One set per harness

Codex cannot run Claude models, so roles are keyed per harness like stepModels: modelRoles.claude.deep, modelRoles.codex.deep. The assistant fills the harness you use. A harness without roles keeps today's fallbacks.

Per-node or per-run pick› Project or team policy› The slot's own setting
stepModels, titleModel…› Its role in modelRoles› Today's per-slot fallback

The assistant writes only modelRoles and clears nothing else. A slot someone set by hand keeps winning. Change the Everyday model once on the Models page and every job on that role follows.

Running it again, and how to build it

Entry points

  • First start. A fresh install (the same test as effectiveUiLevel's "fresh") opens the assistant before the welcome dialog. Its last screen is the welcome dialog's three doors, so onboarding continues where it does today.
  • Settings › General › Setup assistant. A Simple-level row: "Network, models and limits in one pass" with Run setup again. Also in the account menu while a step is broken.
  • Fix-it links. A "proxy needs login" stop, a Copilot "needs sign-in" pill or a model that fails its test opens the assistant on that one step.
  • CLI. worca setup asks the same questions in the terminal for headless and Docker hosts; worca setup --from acme-setup.json applies a team setup and asks only for what it leaves out.
  • Team updates. "Your team updated the recommended setup · Review" in the account menu opens it on Review.

On a re-run

  • Opens pre-filled with the current values, never with detection results that would undo them.
  • Rows that differ from what is saved get a "Changed" chip; Review lists only those, and Apply writes only those.
  • A slot set by hand that disagrees with its new role shows once: "Implement uses gpt-5.5, set on the Models page. Keep it / Use Everyday coding".
  • Skipping a step keeps its saved values. Nothing is cleared unless the person turns it off.

Server work

  • GET /api/setup/detect: the machine checks in one call (preflight already has most of them).
  • POST /api/setup/apply: validates every patch first, then writes in one persistSettings, then runs the side effects in order and streams each result over the WebSocket. A failed step leaves earlier writes in place and says which one to retry.
  • Proxy without a restart: see the section below.
  • Team setup: setup.json read from a link, a file, ~/.worca-cc/team-setup.json or a policy home, plus an editor on the Team policy page.
  • modelRoles.<engine>.{deep, everyday, quick}, keyed per engine like stepModels, in SETTINGS_POST_KEYS, one resolver used by step models, helper jobs, Chat and naming, and a Roles card at the top of the Models page.

UI rules it follows

  • Uses the house dialog anatomy (.dlg-head / .dlg-body / .dlg-foot), 32px fields, divided rows, sentence case.
  • Works at every interface level: it writes Expert-only settings, but never asks the person to switch mode to answer.
  • Never stores a proxy password; the Copilot notice is shown in full and acknowledged, exactly as on the Providers page.
  • The Getting started tile "Connect Claude Code" ticks from the same detection, so the two never disagree.

Changing the proxy without a restart

This is possible, and most of the work already exists. Agents, git, MCP servers and plugins never see the corporate proxy. They are handed HTTPS_PROXY=http://127.0.0.1:<port>, Worca's local proxy, and only that proxy talks to the corporate one. As long as the local address stays the same, everything behind it can change while children keep running.

Agent, git, MCP server› 127.0.0.1:49731
stays the same› Connector
swapped in place› proxy.acme.example:8080

The saved login already works this way: reloadLogin() in src/core/egress-policy.mjs watches proxy-login.json and calls connector.useLogin() without a restart. The rest of the settings can follow the same path.

Team setup

A lead publishes what should be the same for everyone: which models do which work, spend limits and conventions. Network and model access stay personal, because people on one team reach the internet and pay for models in different ways. Teammates see the team's values marked Team in the assistant.

Where it comes from

  • A link or a file on the first screen: "Start from a team setup". Works before any project is added.
  • A file put there by IT: ~/.worca-cc/team-setup.json, or WORCA_TEAM_SETUP pointing at one. Found during the machine check.
  • A team policy home: a new Setup field group in policy.json on the worca-policy branch, using the policy registry's existing kinds and validator. Roles there apply to runs on that repository directly. For the rest, adding the project offers "Your team has a recommended setup" and opens the assistant on the rows that differ.
  • CLI: worca setup --from <url|file>, for Docker images and provisioning scripts.

Editing it

  • The Team policy editor gains a Setup tab from its one-tab-per-group rule, with a kind per value. Publishing is the normal policy commit, so authority stays push permission on worca-policy. The standalone file is the same document limited to the Setup and cost fields.
  • At the end of the assistant, Share as team setup turns your answers into a draft: network and model sources left out, your role picks turned into upstream model names. Save it as a file, or open it in the policy editor.
  • Model roles also join the policy's model section, next to allowed models and step defaults, so a team can change Everyday coding for everyone in one edit.

When the team changes it

  • Worca reads policy on start and every hour, as today. A changed setup shows one line in the account menu: "Your team updated the recommended setup · Review".
  • Review opens the assistant on Review, listing only the changed rows, each marked Team. Nothing is applied until you press Apply.
  • A value you changed yourself stays yours. A soft value you moved away from is listed as a deviation, as allowed models are today.
