Worca design proposal

Worca Credential Broker

Model credentials move out of the worca container into a small broker service. Each person on a shared instance uses their own keys, every model call is charged to the person who caused it, and no agent can read a key.

Status Draft for review Date 2026-09-26 Baseline @worca/app 1.5.0 + dev at abd655d0 Component name worca broker

1Motivation

A hosted worca today runs on one set of model credentials. CLAUDE_CODE_OAUTH_TOKEN or ANTHROPIC_API_KEY sits in the worca container's environment, and spawned agents inherit it. That causes two problems.

  • A team can't share an instance without sharing a key. docs/remote-access.md says so today: "use one deployment per person or per set of credentials". A shared key means one bill, no way to tell who spent what, and one leak affecting everyone.
  • Agents can read the key. In the local compose setup (docker/compose.yml:38-39) and in any setup without agent isolation, an agent can run echo $ANTHROPIC_API_KEY. A prompt injection in a repository, issue or web page can then send the key anywhere the agent has network access.

The broker fixes both with one change. Keys live only in a separate container, and agents hold a short-lived token that only works inside the instance.

2Goals, non-goals, threat model

Goals

  • G-team. A team of developers shares one instance. Each person uses their own model credentials, and costs can be told apart per person.
  • G-leak. A rogue agent or a prompt injection can't read or leak any model credential.
  • One design for every container platform (Compose, Kubernetes, Railway, a Mac mini). Nothing is platform-specific in code.
  • No change for native, non-container installs.

Non-goals

  • Multi-tenancy. Projects, workflows, models, plugins, guardrails and settings stay shared.
  • Privacy between teammates. Everyone still sees all runs, chats, transcripts and code.
  • Per-user permissions or an admin role.
  • Guaranteeing costs are charged correctly when a teammate acts in bad faith.
  • Per-user GitHub identity by default. Pushes and PRs keep the deployment's App or token unless the operator turns on the optional push as me (§10).

Threat model

ActorTrustedWhat the design protects against
Teammates signed in through the identity proxyYesNothing beyond accurate cost attribution. Mistakes are fine.

Worst case with a rogue agent: it spends credits (capped by budgets and limits). It never gets a key.

5How it works

5.1 Guarantees

G-leak rests on four guarantees. Each one follows from how the pieces are arranged, so it doesn't depend on anyone following a procedure. Everything else in this design protects tokens, which can only be used to spend inside the instance.

#GuaranteeHow it's enforced
K1No model credential exists anywhere an agent can reach.Keys exist only in the broker container. worca refuses to start in broker mode if it finds a credential in its env, in ~/.claude (server or agent HOME), in the model catalog, or in provider settings (§6.8).
K2The broker alone decides where each credential is sent.Each credential slot has a fixed upstream origin in the broker's config. Requests name a slot, never a host. Nothing worca can change (the catalog, an Ask proposal, an agent's env) can redirect a key.
K3What an agent holds is worthless outside the instance.Per-spawn wbt_ tokens are accepted only on the broker's private port, expire, and are revoked when the process exits.
K4The broker never sends a credential back.Allowlisted response headers only. Error bodies are scrubbed of the key and of known key shapes (for example OpenAI's Incorrect API key provided: sk-ab…xyz).

5.2 Lifecycle of one spawn

Every claude process worca starts follows the same path: pipeline phases, Ask turns, title generation, the Models Test button, script-runner steps.

sequenceDiagram
  autonumber

  participant A as claude agent
  participant P as api.anthropic.com
  U->>S: Start run (Access JWT = alice@acme.dev)
  S->>S: billTo = alice@acme.dev, slot = anthropic
  S->>B: POST /internal/tokens {billTo, slots, spawnId, ttl}
  B-->>S: wbt_token, expiresAt
  S->>A: spawn with ANTHROPIC_BASE_URL=broker/p/anthropic and ANTHROPIC_AUTH_TOKEN=wbt_token

  B->>B: token valid, slot allowed, path allowed, limits ok
  B->>P: same body, x-api-key = Alice's key

  B-->>A: SSE stream (headers allowlisted), usage recorded for Alice
  A-->>S: process exits
  S->>B: DELETE /internal/tokens/spawnId
  • Why a token per spawn and not per run. A run can wait days for an answer, and each phase is a new process anyway. A per-spawn token can be short-lived and is revoked the moment its process exits.
  • Sub-agents started with the Task tool inside the same claude process share its token. That's intended: they're part of the same spawn.
  • Bridged models (OpenAI, Copilot, local) still go through worca's in-process translation bridge. The CLI sends the wbt_ token to the bridge, the bridge forwards it to broker/p/<slot>, and the broker adds the key. Translation stays in worca; only the credential moves.

  • OpenRouter's dialect stays in the bridge. OpenRouter models are openai-provider entries whose base URL is OpenRouter's (src/core/bridge/openrouter.mjs). The bridge keeps building the request: usage: {include: true}, reasoning, provider routing, the models fallback list. In broker mode it resolves the openrouter slot from that base URL. The broker only swaps credentials, and its request-header allowlist adds OpenRouter's attribution headers (HTTP-Referer, X-Title).
  • Model discovery goes through the broker too. The Models view's import from a Copilot, OpenAI-compatible or OpenRouter endpoint (bridge/providers/endpoint.mjs, provider-ops.mjs) runs in the server. In broker mode it calls /p/<slot>/… with an auxiliary token billed to the person who clicked, never with a key held by worca.

Operators can add slots (another OpenAI-compatible gateway, for example) in the broker's slots file. A slot is either per-person (each teammate saves their own credential) or operator (one credential or none, used by everyone; meant for keyless local models). Operator slots with a real key are off by default in multi mode, because a shared key is exactly what G-team removes.

5.4 Tokens

  • Format. wbt_ followed by 43 base64url characters (32 random bytes). The prefix exists so the token can be redacted everywhere (§6.10).
  • Issued by the broker when the server calls it with the shared secret. The broker stores only a SHA-256 of each token, along with billTo, the slots it may use, spawn/run/thread ids, the issuing server's boot id, expiry, and a spend budget.
  • Lifetime by spawn kind: auxiliary calls 10 minutes, Ask turn 2 hours, pipeline phase 24 hours. All are capped by WORCA_BROKER_TOKEN_MAX_TTL (default 48 h).
  • Revocation:
    • When the process exits, on every exit path.
    • In bulk for a previous server instance: on boot the server revokes everything issued under its old boot id.
    • In bulk for one person, from the broker's admin CLI.
  • Where a token works: only on the proxy routes of the private port. A token can never call /internal/* or the key page.

5.6 Entering keys

People manage their keys on the broker's own page, at its own hostname (worca-01-keys.worca.dev), opened as a normal browser tab. worca shows each person's credential status natively and links to the page.

Decision: no iframe

An earlier draft embedded the key page in worca. It's dropped for three reasons:

  • Cloudflare's Access login page refuses to be framed, so the first visit would show a blank frame.
  • Browsers increasingly block the third-party cookies Access needs inside a frame.
  • A frame gives no protection against a lookalike form anyway.

A top-level page with a visible address is simpler and more robust. The key page therefore sends frame-ancestors 'none'.

  • The broker verifies the Access JWT itself, with its own application audience. It never trusts worca for identity.
  • Keys can be written but never read back. The page shows the last 4 characters, when the key was added, when it was last used, and the last verification result.
  • Save checks the key first with one cheap call (for Anthropic: GET /v1/models), so a typo fails immediately.
  • Copilot sign-in uses GitHub's device-code flow, run entirely by the broker page. The GitHub token never reaches worca.

5.7 When a credential is missing or a budget runs out

  • Before starting: a run whose nodes need a slot the person hasn't filled is refused before any spawn, with a link to the key page. Ask shows the same message for the selected model.
  • During a run: a key that's deleted, a revoked token or a spent budget comes back as a broker error whose message starts with worca-broker:. The run pauses as Needs credential or Budget reached instead of failing, and resumes once the person fixes it (§6.9).

6Code design

Repo conventions that apply
  • No new runtime dependencies. The broker uses node:http, node:crypto and node:sqlite only, like docker/egress-proxy.mjs and src/core/db.mjs.
  • Pure parts are exported for node:test. The server starts only from its entry point.
  • Log lines never carry secret values. Use describeModelEnv-style <set, N chars>.
  • Configuration errors exit with code 78 (EX_CONFIG) and a one-line fix, like remote-access.mjs.

Proxy handling, in order

  1. Reject malformed requests: absolute-form targets, CONNECT, bodies over 32 MB. The Host header is never used for routing.
  2. Split /p/<slot>/<rest>. Reject unknown slots. Normalise <rest> and reject .., //, %2f, %5c, backslashes and control characters. The method and path must match the slot's allowlist exactly; query strings are allowed.
  3. Check the token. Read it from x-api-key or Authorization; it must start with wbt_. Hash it and look it up: not expired, not revoked, and the slot is in the token's list. Otherwise answer 403 (see §6.9 for why never 401).
  4. Apply limits (§6.9 for the error shapes).
  5. Resolve the credential: vault entry for (billTo, slot), or the operator credential, cached in memory for at most 30 s. Missing → 403 with the key page URL.
  6. Build the upstream request to slot.upstream + rest. Copy request headers by allowlist: content-type, accept, anthropic-version, anthropic-beta, user-agent, x-stainless-*, openai-beta. Then add the auth. Nothing else from the agent passes through.
  7. Send with manual redirects. Any 3xx becomes 502 worca-broker: upstream redirect refused.
  8. Return the response: the status, plus headers by allowlist (content-type, request-id, x-request-id, retry-after, anthropic-ratelimit-*, x-ratelimit-*).
    • Success bodies stream through with backpressure. The usage tap reads SSE events without buffering the stream.
    • Error bodies (status 400 and above) are buffered up to 64 KB, scrubbed, then sent.
  9. Record usage and log. Write one usage row. Log one line: time billTo slot model status in/out tokens ms. Never bodies, never headers.

6.5 Storage schema (broker)

CREATE TABLE credentials (
  bill_to TEXT NOT NULL, slot TEXT NOT NULL,
  ciphertext BLOB NOT NULL, iv BLOB NOT NULL, tag BLOB NOT NULL,  -- AES-256-GCM, AAD = bill_to || '\n' || slot
  key_id TEXT NOT NULL,              -- first 8 hex of SHA-256(vault key): lets the broker detect a key change
  suffix TEXT NOT NULL,              -- last 4 characters, for display
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  last_used_at TEXT, verified_at TEXT, verify_error TEXT,
  daily_usd REAL, monthly_usd REAL,  -- personal caps, NULL = operator default
  PRIMARY KEY (bill_to, slot));
CREATE TABLE tokens (
  hash TEXT PRIMARY KEY,             -- SHA-256 hex of the wbt_ token
  spawn_id TEXT NOT NULL UNIQUE, run_id TEXT, thread_id TEXT, kind TEXT NOT NULL,
  bill_to TEXT NOT NULL, slots TEXT NOT NULL,   -- JSON array
  issuer TEXT NOT NULL,              -- worca server boot id
  created_at TEXT NOT NULL, expires_at TEXT NOT NULL, revoked_at TEXT,
  budget_usd REAL, spent_usd REAL NOT NULL DEFAULT 0);
CREATE TABLE usage (
  id INTEGER PRIMARY KEY, at TEXT NOT NULL, bill_to TEXT NOT NULL, slot TEXT NOT NULL,
  spawn_id TEXT, run_id TEXT, model TEXT, status INTEGER,
  input_tokens INTEGER, output_tokens INTEGER, cache_read_tokens INTEGER, cache_write_tokens INTEGER,
  usd REAL, ms INTEGER);
CREATE INDEX usage_bill_to_at ON usage (bill_to, at);
  • bill_to is the lower-cased email from the verified JWT, or local in single mode.
  • Expired token rows are deleted hourly.
  • Usage rows are kept for 400 days.

6.7 worca boot sequence in broker mode

  1. Read WORCA_BROKER_URL and the secret. A URL without a secret exits 78.
  2. Run the credential guard (§6.8). Any finding exits 78.
  3. GET /internal/info, retrying for up to 60 s (the broker may start later). Unreachable or a wrong secret exits 78 with the one-line fix.
  4. POST /internal/tokens/revoke {issuer: previousBootId}. Store the new boot id.
  5. Log credentials: broker multi, key page https://worca-01-keys.worca.dev, slots anthropic, openai.

6.9 Error contract

The broker answers in the Anthropic error envelope for Anthropic-protocol slots, and the OpenAI envelope for OpenAI-protocol slots, so both the CLI and the bridge understand it. Messages always start with worca-broker:.

SituationStatus and typeMessageExisting worca class
No credential for this person and slot403 authentication_errorworca-broker: no Anthropic API key for alice@acme.dev. Add one at https://worca-01-keys.worca.devauth: pause
Stored credential rejected upstream403 authentication_errorworca-broker: your Anthropic API key was rejected by the provider. Replace it at …auth: pause
Token missing, unknown, expired or revoked403 authentication_errorworca-broker: token expired or revokedauth: pause (resume mints a new token)
Path or method not allowed, or slot not in token403 permission_errorworca-broker: POST /v1/files is not allowed for slot anthropicnone: fails
Budget reached403 permission_error (not 429, so the CLI doesn't retry in a loop)worca-broker: quota reached: daily budget of $50 for alice@acme.dev on anthropicquota: pause
Concurrency or rate limit429 rate_limit_error + retry-afterworca-broker: too many concurrent requests, retry after 5 secondsrate_limit: retried by recovery-backoff.mjs
Upstream unreachable or redirected502 api_errorworca-broker: upstream unreachablenetwork: retried
  • Why 403 and never 401. Measured against the real CLI (2.1.283) during implementation: a 401 is retried up to ten times with growing backoff, so a spawn for a person with no key hung for minutes. A 403 stops at once, and the CLI prints Failed to authenticate. API Error: 403 worca-broker: …. The body keeps authentication_error as its type.
  • Why the wording matters. classifyError reads the message text:
    • 401, authentication_error and the broker's own credential messages (worca-broker: no … key for …, token expired or revoked) mean auth;
    • quota means quota;
    • 429 and "rate limit" mean rate_limit.
    So the budget message must say "quota" and must not contain "limit … reset", which would make it usage_limit.
  • Retry timing. recovery-backoff.mjs reads a "retry after N seconds" hint from the message, so the broker writes the wait into the text as well as the retry-after header.
  • Tests: assert each message against classifyError, brokerHint and the backoff parser.

9Cloudflare Access and Railway for the key page

This extends docs/remote-access.md and docs/deploy-railway.md; everything already there stays. The examples use the worca hostname worca-01.worca.dev, the key page hostname worca-01-keys.worca.dev and the Zero Trust team acme.

9.1 Pick the hostname

  • Use a first-level name: worca-01-keys.worca.dev, not keys.worca-01.worca.dev. Cloudflare's free Universal SSL certificate covers one subdomain level. A two-level name needs Advanced Certificate Manager.
  • Nothing else constrains the name. The key page isn't embedded in worca, so it doesn't need to share a site with it.

9.2 Tunnel: a second public hostname

Use the existing tunnel and cloudflared service; no second connector is needed.

  1. Cloudflare One → Networks → Tunnels → your worca tunnel → Public hostnames (newer dashboards: Published application routes) → Add.
  2. Set Subdomain worca-01-keys, Domain worca.dev, Service HTTP, URL broker.railway.internal:8081. Cloudflare creates the DNS record.
  3. Never add a route to port 8080.

With the API (see remote-access.md for the token permissions), the ingress list becomes:

PUT /accounts/{account}/cfd_tunnel/{id}/configurations
{"config": {"ingress": [
  {"hostname": "worca-01.worca.dev",      "service": "http://worca.railway.internal:4317"},

9.3 Access application B

  1. Access controls → Applications → Add an application → Self-hosted. Name it worca-01 keys. Hostname worca-01-keys.worca.dev. Session duration 24 hours.
  2. Policy: attach the same reusable Allow policy as worca's application, so the same people are allowed on both.
  3. Service Auth policy (optional): add one for the service token that worca-railway verify uses. It reaches only /healthz and /api/me, which returns 403 for a service identity.
  4. No Bypass policies. The broker has no route that needs one.
  5. AUD tag: copy the application's Application Audience (AUD) tag. This is the broker's WORCA_CF_ACCESS_AUD, and it's different from worca's.

API equivalent: POST /accounts/{account}/access/apps with {"type":"self_hosted","name":"worca-01 keys","domain":"worca-01-keys.worca.dev","session_duration":"24h","policies":[{"id":"<allow policy id>","precedence":1}]}. The response's aud is the value.

Why a separate application

A token issued for worca's application is refused by the broker, and a token for the key page is refused by worca. A bug or a leaked header on one side can't be replayed against the other.
