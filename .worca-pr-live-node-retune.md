# Live node retune: repoint an agent node's model while the run is in flight

Change one agent node's model and effort on a run that is already running. The
next execution of that node picks the new setting up; an execution already
spawned keeps the argv it launched with. Nothing outside this run moves — the
saved workflow and the run's own default are untouched.

## Using it

**Graph card.** On the live run detail, clicking an agent card opens a popover
with a model and an effort select. Effort is filtered to the chosen model's own
levels. Apply takes effect on that node's next execution.

**Chat.** `/retune [*ref] <nodeId> <model|-> [effort|-]` — `-` clears the model
back to inherit, and an omitted effort resets it to the model's default. The
model token is required, so a typo that eats it cannot silently wipe the
node's setting.

**HTTP.** `POST /api/retune { runId, nodeId, model, effort }`. `model` is
required; `""` is the deliberate clear.

## When a node is retunable

One rule, shared by the engine, the popover, the graph's cursor affordance and
the run detail's chrome (`src/shared/graph/retune-gate.mjs`):

- It is an **agent** node. A flow card spawns nothing, so there is no model to
  change — the panel says so rather than being a dead click.
- The run can still **dispatch**. Past done, stopped or error there is no next
  execution for a new model to reach. Paused and interrupted runs stay
  retunable: they resume, and a pause-killed execution is re-invoked from
  scratch.
- The node has no execution **in flight**. A node that finished one cycle and
  will be re-fired by a loop is editable, which is where retuning is worth the
  most.

The selection is validated against the project's model catalog through the same
validator the composer's own node and step saves use, so a pick the composer
refuses cannot be smuggled onto a running node.

## What it writes

The change patches the node context the scheduler reads, the run's stepper
manifest, and the resume point — so a retune applied to a paused run survives
into the resumed one. A cell the run actually changed is marked, and the pill
carrying it turns amber with a tooltip: on History, where the manifest is a
frozen artifact, that marker is the only record that a node did not run on the
same model throughout.

A write that does not reach the database is reported rather than answered with
a flat success, because an unsaved retune is live in the server process and
gone on the next resume.

## What it shows

Each agent card carries a pill with the node's effective model and effort,
resolved to the catalog's display name. It shares its formatter with the Agents
tab and the compact run card, so the three never spell one selection three ways.
A node whose project is not the selected one resolves against its own catalog.

The change reaches every open browser on the ordinary run state frame — there
is no dedicated event type. A popover left open while a retune lands from chat
or another tab is told, so Apply cannot quietly revert it.
